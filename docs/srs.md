# Software Requirements Specification (SRS)
## Інтелектуальна система складського обліку для малого бізнесу з автоматизованим розпізнаванням накладних постачальників

Версія: 1.0 (фінальна, після аудиту)

### 1. System Context

Система є веб-платформою складського обліку одного орендаря (підприємства малого бізнесу), що взаємодіє із зовнішнім середовищем через чітко визначені межі (Scope):

- **Власник підприємства** — керує каталогом, переглядає звіти, отримує Telegram-сповіщення.
- **Працівник (оператор)** — завантажує накладні, підтверджує розпізнані дані.
- **Постачальник** — не має прямого доступу до системи; є джерелом первинного документа (накладної), що надходить поза електронним каналом системи.
- **Зовнішній LLM/Vision API** — приймає зображення/PDF накладної та повертає структуровані дані; взаємодія захищена мінімізацією персональних даних (SRS-NFR-SEC-03).
- **Telegram Bot API** — канал сповіщень про мінімальні залишки.
- **S3-сумісне сховище (MinIO)** — зберігання оригіналів завантажених документів.
- **Identity Provider (внутрішній, OAuth2/OIDC)** — видає JWT-токени для автентифікації користувачів.

Поза межами системи: бухгалтерський/податковий облік, пряма інтеграція з ERP-системами постачальників (EDI).

### 2. Functional Requirements

| ID | Вимога |
|---|---|
| <a id="srs-fun-01"></a>SRS-FUN-01 | Система повинна надавати CRUD-операції над каталогом товарів та постачальників з підтримкою алісів найменувань. |
| <a id="srs-fun-02"></a>SRS-FUN-02 | Система повинна приймати завантаження файлу накладної у форматі фото (JPEG/PNG) або PDF, перевіряти його на відповідність дозволеному типу та розміру, і зберігати оригінал у S3-сумісному сховищі. |
| <a id="srs-fun-03"></a>SRS-FUN-03 | Система повинна асинхронно розпізнавати позиції накладної (OCR+LLM) і повертати результат у структурованому форматі JSON за фіксованою схемою з полем довіри (confidence) для кожної позиції. |
| <a id="srs-fun-04"></a>SRS-FUN-04 | Система повинна зіставляти розпізнані найменування з каталогом товарів методом гібридного пошуку (нечіткий пошук pg_trgm + векторні ембедінги pgvector) і повертати ранжований список кандидатів з показником релевантності. |
| <a id="srs-fun-05"></a>SRS-FUN-05 | Система повинна надавати інтерфейс підтвердження розпізнаних даних користувачем перед атомарним записом у реєстр руху товарів (Human-in-the-loop), виділяючи поля з показником довіри нижче порогового значення. |
| <a id="srs-fun-06"></a>SRS-FUN-06 | Система повинна вести незмінний (append-only) журнал операцій (прихід/списання/продаж) та атомарно розраховувати поточні залишки з контролем конкурентного доступу (optimistic locking). |
| <a id="srs-fun-07"></a>SRS-FUN-07 | Система повинна відстежувати мінімальні залишки товарів і надсилати Telegram-сповіщення із прогнозом дати вичерпання запасу на основі історичної швидкості витрачання. |
| <a id="srs-fun-08"></a>SRS-FUN-08 | Система повинна формувати звіти руху товарів за довільний період з розмежуванням доступу за роллю користувача (власник/працівник) відповідно до RBAC-матриці. |

### 3. Non-Functional Requirements

| ID | Категорія | Вимога |
|---|---|---|
| <a id="srs-nfr-perf-01"></a>SRS-NFR-PERF-01 | Продуктивність | API повинен забезпечувати Latency p95 ≤ 200 мс при сталому навантаженні 100 RPS. |
| <a id="srs-nfr-perf-02"></a>SRS-NFR-PERF-02 | Продуктивність | Повний цикл асинхронної обробки однієї накладної (до 30 позицій) повинен не перевищувати 15 секунд від моменту завантаження до появи результату в інтерфейсі підтвердження. |
| <a id="srs-nfr-scale-01"></a>SRS-NFR-SCALE-01 | Масштабованість | Черга задач повинна витримувати до 50 одночасних задач розпізнавання з гарантією доставки at-least-once і без втрати повідомлень при перезапуску воркера. |
| <a id="srs-nfr-sec-01"></a>SRS-NFR-SEC-01 | Безпека | Автентифікація повинна здійснюватися через OAuth2/OIDC з виданням JWT, час життя access-токена ≤ 15 хвилин, refresh-токена ≤ 7 днів. |
| <a id="srs-nfr-sec-02"></a>SRS-NFR-SEC-02 | Безпека | Авторизація повинна реалізовуватись через RBAC на рівні кожного API-ендпоінта з явним розмежуванням ролей «власник» / «працівник». |
| <a id="srs-nfr-sec-03"></a>SRS-NFR-SEC-03 | Безпека | Персональні дані контрагентів (назва, реквізити) у зображенні накладної повинні маскуватись або мінімізуватись перед передачею до зовнішнього LLM API. |
| <a id="srs-nfr-sec-04"></a>SRS-NFR-SEC-04 | Безпека | Публічні API-ендпоінти повинні обмежуватись Rate Limiting (не більше 100 запитів/хв на один токен) для запобігання DoS-навантаженню. |
| <a id="srs-nfr-sec-05"></a>SRS-NFR-SEC-05 | Безпека | CI/CD-конвеєр повинен включати Trivy (сканування образів) та статичний аналіз коду SonarQube як обов'язковий Quality Gate, що блокує злиття при критичних знахідках. |
| <a id="srs-nfr-rel-01"></a>SRS-NFR-REL-01 | Надійність | Інфраструктура повинна розгортатися через Docker Compose з підтримкою горизонтального масштабування воркерів обробки незалежно від API-шару. |
| <a id="srs-nfr-rel-02"></a>SRS-NFR-REL-02 | Надійність | Зовнішні викликии до LLM API повинні захищатись патерном Circuit Breaker з фіксованим порогом помилок перед переходом у стан Open. |
| <a id="srs-nfr-rel-03"></a>SRS-NFR-REL-03 | Надійність | Задачі, що не вдалося обробити після вичерпання спроб retry з експоненційною затримкою, повинні потрапляти у Dead Letter Queue для подальшого ручного розбору. |
| <a id="srs-nfr-rel-04"></a>SRS-NFR-REL-04 | Надійність | База даних повинна резервуватись щодобово автоматизованим завданням з retention не менше 14 днів і періодичною перевіркою відновлюваності бекапу. |

### 4. Verification Criteria

| ID вимоги | Метод верифікації |
|---|---|
| SRS-FUN-01…08 | Автоматизовані інтеграційні тести (pytest + Testcontainers) на кожен ендпоінт; покриття критичного шляху ≥ 80%, перевірка через CI на кожен PR. |
| SRS-NFR-PERF-01, 02 | Навантажувальне тестування k6 за сценарієм Spike Testing з фіксацією p95/p99 latency у звіті CI. |
| <a id="srs-nfr-scale-01"></a>SRS-NFR-SCALE-01 | Тест стійкості черги RabbitMQ під навантаженням (k6 + симуляція kill воркера), перевірка відсутності втрати повідомлень через підрахунок acked/unacked. |
| SRS-NFR-SEC-01, 02 | Автоматизовані auth-тести (pytest) на прострочення токена, оновлення через refresh та заборонений доступ за роллю. |
| <a id="srs-nfr-sec-03"></a>SRS-NFR-SEC-03 | Код-рев'ю та unit-тест на маскування PII-полів перед серіалізацією запиту до LLM API. |
| <a id="srs-nfr-sec-04"></a>SRS-NFR-SEC-04 | Навантажувальний тест k6 з перевищенням лімітів запитів, очікується HTTP 429 понад порогом. |
| <a id="srs-nfr-sec-05"></a>SRS-NFR-SEC-05 | Звіт сканування Trivy (критичні CVE = 0) та Quality Gate SonarQube в GitHub Actions як блокуючий крок пайплайну. |
| SRS-NFR-REL-01, 03 | Симуляція падіння воркера (chaos-тест) з перевіркою автоматичного перезапуску контейнера та потрапляння незавершеної задачі у DLQ. |
| <a id="srs-nfr-rel-02"></a>SRS-NFR-REL-02 | Unit-тест Circuit Breaker: примусова симуляція N послідовних помилок LLM API, перевірка переходу в стан Open і відмови без реального виклику. |
| <a id="srs-nfr-rel-04"></a>SRS-NFR-REL-04 | Автоматизована перевірка наявності та відновлюваності бекапу БД у CI/CD-скрипті (cron job + тестове відновлення в ізольоване середовище). |

### 5. Glossary

| Термін | Визначення |
|---|---|
| OCR (Optical Character Recognition) | Технологія розпізнавання тексту із зображення. |
| LLM (Large Language Model) | Велика мовна модель, що використовується для структурування розпізнаного тексту у JSON. |
| pgvector | Розширення PostgreSQL для зберігання та пошуку векторних ембедінгів. |
| JWT (JSON Web Token) | Формат токена автентифікації, що містить підписані claims користувача. |
| Idempotent Consumer | Патерн обробки повідомлень, що гарантує відсутність дублювання ефекту при повторній доставці. |
| Transactional Outbox | Патерн запису події в тій самій транзакції, що й основна сутність, для гарантованої публікації. |
| Circuit Breaker | Патерн відмовостійкості, що тимчасово блокує виклики до нестабільного зовнішнього сервісу після серії помилок. |
| Dead Letter Queue (DLQ) | Черга для повідомлень, обробку яких не вдалося завершити після вичерпання спроб повторів. |
