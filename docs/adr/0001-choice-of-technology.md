# ADR-001: Вибір сховища для векторних ембедінгів найменувань товарів

**Статус:** Approved

## Context

Для реалізації гібридного зіставлення найменувань (SRS-FUN-04) системі потрібно зберігати та шукати за косинусною/евклідовою схожістю векторні ембедінги назв товарів з каталогу постачальників. Обсяг даних — каталог малого торговельного підприємства, порядку тисяч SKU, а не мільйонів. Задача обмежена вимогами SRS-NFR-PERF-01/02 (p95 ≤ 200 мс, цикл обробки накладної ≤ 15 с) та SRS-NFR-SEC-03 (мінімізація передачі даних зовнішнім сервісам).

## Alternatives

1. **pgvector** — розширення PostgreSQL для зберігання та ANN/brute-force пошуку векторів у тій самій БД, що й основні дані.
2. **Виділена векторна БД (Pinecone, SaaS)** — спеціалізований хмарний сервіс векторного пошуку з тарифікацією за обсяг/запити.
3. **Виділена векторна БД (Weaviate / Qdrant, self-hosted)** — окремий контейнеризований сервіс з розширеними ANN-алгоритмами (HNSW з квантизацією).

## Decision

Обрано **pgvector**.

Технічне обґрунтування:
- **ACID-консистентність:** запис товару та його ембедінгу відбувається в єдиній транзакції СУБД, що унеможливлює розсинхронізацію між основними даними та вектором — проблему, неминучу при двох окремих системах зберігання (альтернативи 2 і 3).
- **Операційна простота:** не додає нового контейнера, нової точки моніторингу, нової процедури бекапу — усе покривається вже наявною інфраструктурою PostgreSQL (SRS-NFR-REL-04).
- **FinOps:** Pinecone тарифікується за обсяг і кількість запитів (додаткові операційні витрати без відповідного виграшу для обсягу в тисячі SKU); self-hosted Weaviate/Qdrant вимагають додаткового обчислювального ресурсу (RAM/CPU) без обґрунтованого приросту якості пошуку на такому масштабі даних.
- **Безпека:** відсутня необхідність передавати ембедінги за межі власної інфраструктури (на відміну від SaaS-альтернативи), що узгоджується з SRS-NFR-SEC-03.
- **Відповідність масштабу:** за обсягу в тисячі (не мільйони) векторів продуктивність pgvector достатня для виконання SRS-NFR-PERF-01/02 без спеціалізованих ANN-оптимізацій.

## Consequences

**Позитивні:**
- Єдина точка зберігання даних і транзакційна цілісність.
- Нижчі операційні витрати (FinOps) та менше Ops Overhead.
- Відсутність Vendor Lock-in до стороннього SaaS-провайдера векторного пошуку.

**Негативні (усвідомлені компроміси):**
- Масштабування векторного пошуку прив'язане до вертикального масштабування самої БД, а не до незалежного горизонтального масштабування, яке надають спеціалізовані векторні БД.
- Відсутні деякі просунуті ANN-алгоритми з квантизацією, доступні в Qdrant/Weaviate — за зростання каталогу до мільйонів SKU (поза заявленим обсягом цієї кваліфікаційної роботи) рішення потребуватиме перегляду.
- У разі майбутнього масштабування поза межі одного орендаря доведеться повторно оцінити це рішення (зафіксовано як відомий технічний борг, а не замовчено).
