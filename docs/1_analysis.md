# 1. АНАЛІТИЧНИЙ ОГЛЯД ТА ОБҐРУНТУВАННЯ АРХІТЕКТУРИ

## 1.1. Інженерний опис аналогів

У межах дослідження проаналізовано три програмні рішення, що домінують на ринку складського обліку: BAS, Poster POS та KeyCRM. Аналіз проводився за системними метриками, протоколами взаємодії та здатністю інфраструктури обробляти неструктуровані дані.

Система BAS базується на класичній архітектурі Client-Server Monolith. Обмін даними для зовнішніх інтеграцій здійснюється через протоколи SOAP та OData. Головним технічним недоліком (Technical Bottleneck) є синхронна модель виконання транзакцій у реляційній базі даних, що призводить до критичного зростання Latency під час масового проведення документів. 

Хмарна система Poster POS використовує сервіс-орієнтовану архітектуру (SOA). Взаємодія компонентів забезпечується через REST API та WebSockets. Зберігання даних реалізовано на базі PostgreSQL та кешування у Redis. Інженерним обмеженням системи є відсутність вбудованого конвеєра обробки неструктурованих даних (IDP). Запити до зовнішніх OCR-сервісів виконуються синхронно, що зумовлює ризик вичерпання пулу потоків (Thread Starvation) у разі збільшення часу відгуку провайдера.

Платформа KeyCRM реалізована за патерном Modular Monolith (Multi-tenant). Обмін даними з маркетплейсами побудовано на базі REST API та Webhooks. Виявлено архітектурну вразливість: відсутність механізмів Dead Letter Queue (DLQ) та патернів ідемпотентності при обробці вхідних Webhooks, що унеможливлює гарантовану доставку подій та вимагає ручної синхронізації у разі мережевих збоїв.

## 1.2. Порівняльний аналіз та обґрунтування технологічного стеку

Таблиця 1.1 — Порівняльний інженерний аналіз архітектурних рішень

| Критерій порівняння | Проєктована система (AI Asset Manager) | BAS | Poster POS | KeyCRM |
| :--- | :--- | :--- | :--- | :--- |
| **Архітектурний патерн** | Modular Monolith + Event-Driven | Client-Server Monolith | SOA / Microservices | Modular Monolith |
| **Протоколи взаємодії** | REST API, AMQP | SOAP, OData, TCP | REST API, WebSockets | REST API, Webhooks |
| **Стек бази даних** | PostgreSQL (pgvector, pg_trgm) | MS SQL Server / PostgreSQL | PostgreSQL, Redis | MySQL / PostgreSQL |
| **Обробка документів** | Асинхронний конвеєр (OCR + LLM) | Відсутня / Ручне введення | Ручне / Синхронне API | Ручне введення |
| **Механізм відмовостійкості** | Transactional Outbox, DLQ | Песимістичне блокування СУБД | Відсутній для OCR-інтеграцій | Відсутній (втрата подій) |
| **Середовище розгортання** | Контейнеризація Docker | On-Premise / IaaS | Cloud-native (AWS) | Cloud-native |

**Аналітичний висновок підрозділу 1.2**

Проаналізовані рішення конкурентів спроєктовані переважно для синхронної транзакційної обробки структурованих даних. Використання синхронних REST та SOAP запитів є неефективним для інтеграції ресурсоємних моделей машинного навчання (OCR та LLM), оскільки час виконання таких задач є недетермінованим, що неминуче призводить до зростання затримок (Latency) та нестабільності системи під навантаженням. Окрім того, відсутність у базових СУБД аналогів підтримки векторних індексів унеможливлює реалізацію швидкого семантичного зіставлення номенклатури.

Для вирішення виявлених архітектурних проблем у межах кваліфікаційної роботи обрано стек на базі FastAPI, PostgreSQL та RabbitMQ. Застосування патернів Event-Driven Architecture, зокрема Transactional Outbox та Idempotent Consumer у поєднанні з чергами повідомлень (AMQP), дозволяє ізолювати важкі обчислювальні процеси у фонові worker-и, забезпечуючи високу відмовостійкість (Fault Tolerance) конвеєра. Використання розширення pgvector в ядрі PostgreSQL гарантує високу продуктивність гібридного пошуку без необхідності розгортання додаткових векторних баз даних, що оптимізує споживання інфраструктурних ресурсів.
