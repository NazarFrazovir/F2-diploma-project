# 1. Аналіз предметної області та постановка задачі

## 1.1 Актуальність

Малий бізнес (роздрібні магазини, заклади громадського харчування, аптеки) витрачає значні трудовитрати на ручне приймання накладних постачальників, що призводить до помилок у залишках товарів та втрат через невчасне дозамовлення. Існуючі облікові системи (BAS, Poster, KeyCRM) автоматизують облік лише для підключених постачальників через EDI/API-інтеграції та не вирішують задачу розпізнавання довільної накладної з фотографії.

## 1.2 Огляд сучасних підходів до розпізнавання документів

| Підхід | Переваги | Обмеження |
|---|---|---|
| Класичний OCR (Tesseract, ABBYY) | Низька вартість, локальне виконання | Низька точність на зашумлених фото, не розуміє структуру таблиці |
| Vision-LLM (GPT-4V, Claude, Gemini) | Висока точність структурованого виводу, розуміння контексту таблиці | Вартість запиту, затримка, потреба передачі даних зовнішньому API |
| Гібридний підхід (OCR + LLM-постобробка) | Баланс вартості й точності, можливість offline fallback | Складніша архітектура конвеєра |

Для проєкту обрано гібридний підхід: OCR/vision-модель виконує первинне розпізнавання, а LLM перетворює результат у структурований JSON із валідацією схеми.

## 1.3 Порівняльний аналіз існуючих рішень

| Критерій | BAS | Poster | KeyCRM | Запропонована система |
|---|---|---|---|---|
| Розпізнавання довільної накладної з фото | Відсутнє | Відсутнє | Відсутнє | Є (OCR+LLM) |
| Інтеграція лише з підключеними постачальниками | Так | Так | Так | Не потрібна |
| Гібридне зіставлення найменувань | Відсутнє | Часткове (точний пошук) | Часткове (точний пошук) | Нечіткий + семантичний пошук (pgvector) |
| Підтвердження розпізнаних даних перед записом | Відсутнє | Відсутнє | Відсутнє | Є (Human-in-the-loop) |
| Telegram-сповіщення про залишки | Відсутнє | Відсутнє | Часткове | Є, з прогнозом дозамовлення |

## 1.4 Функціональні вимоги (To-Be, Core Features)

1. CRUD над каталогом товарів/постачальників з алісами найменувань.
2. Завантаження фото/PDF зі зберіганням оригіналів у S3-сховищі.
3. Асинхронне розпізнавання позицій (OCR+LLM) у JSON за фіксованою схемою.
4. Гібридне зіставлення з каталогом (нечіткий пошук + векторні ембедінги) з ранжуванням.
5. Інтерфейс підтвердження розпізнаних даних перед записом.
6. Незмінний журнал операцій (прихід/списання/продаж) та розрахунок залишків.
7. Моніторинг мінімальних залишків та Telegram-сповіщення з прогнозом вичерпання.
8. Звіти руху товарів з рольовим розмежуванням доступу.

## 1.5 Нефункціональні вимоги (NFR)

| Категорія | Метрика |
|---|---|
| Продуктивність | API Latency p95 ≤ 200 мс при 100 RPS |
| Продуктивність | Повний цикл обробки накладної ≤ 15 с (до 30 позицій) |
| Масштабованість | Черга витримує до 50 одночасних задач, at-least-once |
| Безпека | JWT, access-токен ≤ 15 хв; RBAC на рівні API-ендпоінтів |
| Безпека | Мінімізація персональних даних при передачі до LLM API |
| Безпека | Trivy + статичний аналіз як Quality Gate в CI/CD |
| Надійність | Docker Compose, горизонтальне масштабування воркерів |
| Надійність | Dead Letter Queue для необроблених задач |
| Надійність | Бекап БД щодоби, retention ≥ 14 днів |
